# Full-spec standard (every published spec, per robot)

Goal: host EVERY spec a manufacturer (or an authoritative public document) publishes for each robot,
not just the shared key metrics in robots.json. Each robot gets one file: `data/specs/<robot-id>.json`.
`spec_keys.json` is the SUPERSET of every spec key used by any robot (generated by build_specs.py).

## File shape: data/specs/<robot-id>.json
{
  "id": "boston-dynamics-spot",
  "checked": "2026-11-04",                       // date researched (KST)
  "documents": [                                  // every document/page actually opened
    {"title": "Spot Instructions for Use v5.1.5 (Apr 2026)", "url": "https://...pdf"}
  ],
  "specs": [
    {
      "group": "Power",                           // one of GROUPS below
      "key": "battery_capacity",                  // snake_case, GENERIC (never product names)
      "label": "Battery capacity",                // English label as a reader expects
      "value": 564,                               // number when numeric; else string; booleans true/false
      "unit": "Wh",                               // SI-style unit or "" ; keep the source's unit, do not convert
      "note": "",                                 // condition/qualifier: "at 25 °C dock ambient, to 80%", footnotes
      "source": "https://...pdf",                 // the URL the value came from
      "ref": "§1.5.2 p.10"                        // optional: section/page/table in the document
    }
  ]
}

Rules
- Never guess. Only values stated in an opened source. Prefer: manufacturer datasheet/manual/IFU > manufacturer
  product/spec page > manufacturer developer docs > certification filings > reputable press quoting the maker.
- One fact = one row. Ranges: value "−20 to 45" with unit "°C" (string), or split into _min/_max keys.
  A list (e.g. sensors, standards) = one row per item OR a single string joined by "; ".
- Same quantity under different conditions = same key + different `note` (e.g. charge time at 25 °C vs 35 °C).
- Variant differences (Air/Pro/EDU): put them in the variant's own robot file.
- Reuse keys from `spec_keys.json` / the seed list when the meaning matches. Create a new key only for a new
  meaning; make it generic so other robots can share it (e.g. `max_step_height`, not `spot_step_height`).
- Include everything: physical, mobility/terrain limits, power/charging, environment (temp, humidity, IP, altitude,
  wind, rain, lighting), sensors (count, type, FOV, range, resolution, fps), compute (CPU/GPU/RAM/storage),
  connectivity (Wi-Fi bands, Ethernet, LTE/5G, Bluetooth, ports), payload interface (ports, voltage, power,
  rails, bolt sizes, max mass), manipulation (arm DoF, reach, payload, gripper force), joints (DoF per limb,
  torque, joint speed), safety (stop distance, E-stop, safety standards, certifications, PL/SIL), noise (dBA),
  lights/audio, software (OS, SDK, API, ROS version), control (controller, range, modes, autonomy features),
  shipping/case dims and weight, accessories, warranty, price, model/part numbers, software version, compliance.

GROUPS (use exactly these):
Identity · Dimensions & Mass · Mobility & Performance · Terrain & Navigation Limits · Power & Battery ·
Charging & Docking · Environment & Protection · Sensors & Perception · Compute & Software ·
Connectivity & Interfaces · Payload & Mounting · Manipulation · Actuation & Joints · Safety & Compliance ·
Controls & Operation · Audio, Lights & HMI · Transport & Storage · Commercial

Duplicate keys found later are mapped in `spec_key_aliases.json` (old -> canonical); never use an aliased key.

## Comparability (so every field can be ranked, charted and filtered)
- Store numbers as JSON numbers with a `unit` from the build script's unit table (mm, cm, m, kg, lb, m/s, km/h, h, min, Wh, Ah, °, °C, V, W, dB(A) …). A clean string like "550 mm" or "1.2–1.5 m" is parsed too; anything else stays text and shows only in the table.
- `scripts/build_specs.py` converts every parseable row to the key's display unit (`n`, or `lo`/`hi` for ranges) and records `f2b` (display unit → base unit) so mixed-unit sources sort together.
- `data/spec_key_meta.json` holds curated labels and **families** of related keys shown together (e.g. Path & aisle clearance, with overall width as a lower-bound proxy). When a new key belongs to a family, add it there.
